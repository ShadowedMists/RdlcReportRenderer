If revisited, the tile-service question needs its own decision first — a Google Maps adapter (commercial API, usage-based billing) or an OpenStreetMap adapter (tile-server-based, no API key, but self-hosting/usage-policy considerations at production volume) are the two candidate replacements — before any GDI+→interface migration work on Map itself would be worth starting.

**Verification convention** (both engines, every increment): `dotnet build` 0 errors + full test suite (`VisualRegressionTests` + `Chart.Rdl.Tests`) passing + zero baseline PNG diffs. See `docs/rendering-abstractions.md` for the git-stash baseline-generation technique used for previously-uncovered render paths.

## PDF: cross-platform rendering (LOWER PRIORITY)

**Status (2026-07-26): P1-P3 done, P4 re-scoped and much larger than previously estimated.** The 2026-07-24 re-scoping correctly found PDF's own path (`PDFRenderer`→`Renderer`→`PDFWriter`) never touches `Metafile`/`Graphics`/`Pen`/`Brush`/`GraphicsPath` — that machinery belongs to the separate `ImageWriter` (BMP/GIF/JPEG/PNG/TIFF/EMF) extension. What it under-scoped: P4 ("Uniscribe complex-script shaping, ~1,375 lines") is not an RTL/CJK-only concern — `RichText.TextRun.ShapeAndPlace` calls Uniscribe and constructs live GDI+ `Font` objects **unconditionally for every text run, in every script**, with no simple/Latin fast path anywhere in the pipeline. This is PDF's actual, singular remaining blocker, and it's shared infrastructure — the same pipeline backs the Windows-only `ImageWriter`, the WinForms on-screen viewer, and the shared `HPBProcessing`/`SPBProcessing` pagination engines used by every renderer.

**Done (2026-07-26):**
- P1: embedded-image decode now goes through `IImageProvider.DecodeToBgra32` (Excel's `ImageProviderFactory` pattern), not `System.Drawing.Bitmap`/`LockBits`.
- P2: `PDFFont.Style` is `PdfFontStyle`, a local enum, not `System.Drawing.FontStyle`.
- Two extra eager-GDI+-construction bugs found while implementing P1/P3, both fixed: `Renderer.ImageResources` (built at type-load) and `GraphicsBase`'s `Bitmap`/`Graphics` pair (built in its constructor, called by every PDF render's `WriterBase.BeginReport`) are now lazy — a text-free PDF (lines/rectangles/images only) no longer crashes at construction on a GDI+-less platform.
- Verified: `dotnet build` 0 errors, full test suite passing (137 + 2 + 5), a new end-to-end `SunburstChartWithCategoryHierarchy_RendersToPdf` test exercising the real PDF path.

**Done (2026-07-26): both simple and rich (multi-run/multi-paragraph) PDF text boxes render real text on non-Windows.** Tracing "P3"'s font-metrics call sites found they were never independently reachable (gated by P4's blocked RichText pipeline the whole time) — but that same trace found PDF's standard 14 fonts need no embedded data/`/Widths` array at all, unlocking a small, dependency-free MVP: `Renderer.ProcessSimpleTextBox`/`ProcessRichTextBox` now branch on `!OperatingSystem.IsWindows()` to new `WriterBase.DrawWrappedText`/`DrawWrappedRichText`/`PDFWriter` paths (base-14 font resolution + approximate word-wrap, across run boundaries for rich text + direct `Tj` content-stream writing), bypassing RichText/Uniscribe/GDI+ entirely. Center/right text alignment added the same day (line start-x computed from the same approximate width table used for word-wrap). Underline/strikethrough added the same day, closing out the base-14 font work for now — decorations drawn as filled rectangles appended after each `BT`/`ET` block (PDF text objects can't contain path-painting operators), positioned using the same approximate-width tracking as word-wrap. Verified end-to-end (temporarily forced on this Windows dev box, rendered real correct PDFs for all cases, including mixed bold/normal runs, a separately-styled paragraph, centered/right-aligned text, and mixed-decoration rich text). Gaps: font family beyond Arial/Times New Roman/Courier New falls back to Helvetica (explicitly deferred per user direction until PDF rendering is otherwise end-to-end); WinAnsi-only (no arbitrary Unicode); no overline. Full detail: `tasks/pdf-text-shaping-abstraction.md`'s "MVP" section.

**Also done (2026-07-26): this path now has a real automated regression test.** Granted `InternalsVisibleTo` from `Microsoft.ReportViewer.Common` to `Microsoft.ReportViewer.Chart.Rdl.Tests` (already signed with the same key — not a new trust boundary, see `docs/decisions.md`). `CrossPlatformPdfTextTests.cs` calls `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` directly and asserts on the emitted PDF operators, closing the "manual-verification-only" gap noted above for every prior increment.

**Not done — full-fidelity text (rich/multi-run boxes, custom/embedded fonts, RTL/complex scripts) and the Image/WinForms-viewer/pagination engines that share the RichText/Uniscribe pipeline:** genuinely large, new-logic work (a HarfBuzzSharp-based shaper + bidi/line-break implementation), not a resource-type port like Chart/Gauge's migration. Full P/Invoke inventory, blast-radius trace, and a phased plan are in `tasks/pdf-text-shaping-abstraction.md`. Of that plan: the HarfBuzzSharp/SkiaSharp spike, a behavioral verification harness, and now the font-layer port are done (2026-07-26) — `SkiaCachedFont.cs` gives `CachedFont`'s font-metrics surface a Skia-backed equivalent needing no device context (5 tests, `SkiaCachedFontTests.cs`), plus `Microsoft.ReportViewer.Common.csproj` now references SkiaSharp/HarfBuzzSharp directly. It's scaffolding only — nothing calls it yet, since `Hfont` is only ever used to feed Uniscribe, not for metrics alone. The shaping-layer translation (61 `Win32DCSafeHandle` call sites traced across 10 files, since `LineBreaker`/`TextBox` consume Uniscribe-shaped `SCRIPT_ANALYSIS`/`SCRIPT_LOGATTR`/`GlyphShapeData` structures) now has working prototypes for all three sub-problems: `HarfBuzzTextShaper.cs` shapes text via HarfBuzzSharp and translates it into the same `GlyphData`/`GlyphShapeData`/`ABC`/`GOFFSET` shapes Uniscribe produces (6 tests); `UnicodeTextItemizer.cs` splits text into script/direction runs via coarse Unicode ranges, building real `SCRIPT_ANALYSIS` values through the existing `ScriptAnalysis`/`ScriptState` wrapper classes (7 tests — caught and fixed a real `NullReferenceException` from an uninitialized `ScriptState` field along the way); `UnicodeLineBreakAnalyzer.cs` produces `SCRIPT_LOGATTR` per character via a hand-rolled soft-break heuristic (6 tests, needed a new minimal `SCRIPT_LOGATTR.FromFlags` factory since that struct is normally only populated by P/Invoke marshaling). All scoped to plain LTR non-reordering text only (documented gaps: no real Uniscribe script IDs, no UAX #14 line-breaking compliance, `SCRIPT_VISATTR` zeroed, no fallback-font retry). The three prototypes are now composed into one pipeline (`UnicodeParagraphShaper.cs`) — itemize, then shape each item with its own slice of line-break attributes — which surfaced and fixed a real native crash (`0xC0000005` in HarfBuzzSharp, only appearing after many cumulative shape calls across a test run, never within one isolated test) by switching `SkiaCachedFont`/`HarfBuzzTextShaper` to use `SkiaSharp.HarfBuzz.SKShaper` (the same integration package this repo's visual-verification harness already uses successfully) instead of hand-building HarfBuzzSharp's Face/Font from a raw blob. Verified stable across repeated full-suite runs after the fix. **Not yet wired into production** — `FontCache`/`TextRun`/`LineBreaker`/`Paragraph` still exclusively use Win32/Uniscribe on every path; this pipeline is not yet connected to a platform-selection seam.

**Reference:** `tasks/pdf-render-callstack-analysis.md` (historical call-chain trace, now a pointer doc), `tasks/pdf-quick-reference.md` (cheat sheet), `tasks/pdf-text-shaping-abstraction.md` (what's left), `docs/platform-support.md`'s "PDF (RDL engine)" section (current state), `docs/decisions.md` (the 2026-07-24 and 2026-07-26 correction entries).

**Recommendation:** P4 is not a "spike it and estimate" item anymore — it's confirmed as PDF's only remaining blocker and confirmed large. Still lower priority than Chart/Gauge (which are further along and higher-traffic), but it's no longer credible to treat it as smaller than the Map engine's deferred migration — revisit relative prioritization between PDF-P4 and Map next time either is picked up.
