# WebRequest → HttpClient migration (SYSLIB0014)

**Status: DONE except the 3 Map-engine sites (deliberately deferred).** All 7 non-Map sites are now fixed — see "Sites fixed" below. The remaining 3 (`BingMapsService.cs` x2, `MapCore.cs`) are intentionally left alone until the Map engine's own deferred migration is revisited (see `docs/decisions.md`'s Map engine deferral entry); fixing them in isolation ahead of that decision would be wasted effort, per this file's own original scoping.

## Sites fixed (2026-07-27) — `WebRequestHelper.cs` (WinForms + NETCore)

The highest-value/highest-risk sites from the original scoping (`WebRequestHelper.GetServerUrlAccessObject`, both copies) turned out tractable once picked up. Converted to a `HttpResponseMessage`-returning `WebRequestHelper.ExecuteServerUrlRequest(...)`, built from a per-call `HttpClientHandler`/`HttpClient` pair (matching `ExternalResourceLoader.cs`'s established pattern — credentials here are genuinely per-call: impersonated/forms/bearer, not a fixed shared identity):

- `AbortState.cs` (both copies): `m_abortableRequest` changed from `HttpWebRequest` to `CancellationTokenSource`; `AbortRequest()` now calls `.Cancel()` instead of `.Abort()` — same "cancel the same token that bounds the send" pattern already used by `ExternalResourceLoader.cs`, since `HttpClient` has no in-flight abort primitive either.
- `WebRequestHelper.cs` (both copies): `GetServerUrlAccessObject(...):HttpWebRequest` replaced with `ExecuteServerUrlRequest(...):HttpResponseMessage`, taking a `CancellationToken` instead of a `timeout` int (the caller now owns the `CancellationTokenSource`, since it also has to register it with `AbortState`). `SetRequestHeaders(HttpWebRequest, ...)` was deleted outright — confirmed by grep it had zero live callers (its only two call sites were both inside an already-dead, commented-out `GetWebRequest`/`GetWebResponse` override block in `SoapReportExecutionService.cs`).
- `ExceptionFromWebResponse` signature changed from `(Exception):ReportServerException` to `(HttpResponseMessage, Exception):ReportServerException`. This is a real, deliberate behavior change, not a mechanical swap: `HttpWebRequest.GetResponse()` used to throw `WebException` on any non-2xx status, and the old code inspected `WebException.Response` to parse the server's XML `rs:MoreInformation` fault body. `HttpClient` doesn't throw on non-2xx by default, so the caller (`SoapReportExecutionService.ServerUrlRequest`) now explicitly checks `response.IsSuccessStatusCode` and passes the response through for the same fault-body parsing (`TryParseMoreInformationFault`, logic unchanged) — this preserves the original fault-detection behavior rather than silently dropping it, unlike the exception-type-only change accepted for `ExternalResourceLoader.cs`.
- `SoapReportExecutionService.ServerUrlRequest` (both copies): rewritten to build the `CancellationTokenSource` from `m_timeout` (falling back to `System.Threading.Timeout.InfiniteTimeSpan` for a non-positive timeout — `m_timeOut` defaults to 600000 in practice, so this is a defensive fallback, not the common case), register it with `AbortState` before sending, and read `Content-Type`/`FileExtension` off `HttpResponseMessage.Headers`/`Content.Headers` instead of `HttpWebResponse.Headers`. Note `Timeout.InfiniteTimeSpan` had to be fully qualified as `System.Threading.Timeout...` — this class already declares its own `Timeout` property (a `SoapReportExecutionService.Timeout` setter), the same kind of name collision already flagged for `System.Threading.Timer` in the `ExternalResourceLoader.cs` fix.

Verified 2026-07-27: `dotnet build --no-incremental` 0 errors; `SYSLIB0014` count dropped from 6 to the 3 expected Map-engine occurrences (counted twice each — WinForms and NETCore both reference the shared `Microsoft.ReportViewer.DataVisualization` project, so `BingMapsService.cs` x2 + `MapCore.cs` show up as 3 distinct call sites × 2 referencing projects); `Chart.Rdl.Tests` 171/171, `ReportViewerCore.LinuxRenderers.Tests` 15/15, 0 regressions. Not verified under WSL — this is server-connection/HTTP-transport code with no platform-specific rendering path, unlike the PDF text-shaping fix, so a WSL run wouldn't exercise anything a Windows run doesn't already cover; no automated test exercises the actual `SoapReportExecutionService`/report-server connection path either way (it needs a real or mocked report server), which pre-dates this change and isn't a gap introduced by it.

## Why the remaining sites weren't fixed inline

The obsolete-warning cleanup (2026-07-26) fixed the other ~470 obsolete warnings found in a full rebuild directly (DtdProcessing, CaseInsensitiveHashCodeProvider, Enum.ToString(IFormatProvider), XmlConvert date overloads, legacy exception serialization members, etc.), plus — on closer inspection — 3 of the 10 `SYSLIB0014` sites turned out to be simple enough to fix the same way: a bare `WebRequest.Create(uri).GetResponse().GetResponseStream()` GET-and-decode, already wrapped in a swallow-all `try/catch(Exception)`. The remaining 7 sites are a real rewrite of this codebase's synchronous HTTP request/response pipeline (cookies, credentials, POST bodies, custom `IAsyncResult`-based async APIs, hand-rolled cache/timeout/cancellation plumbing) — not a call-by-call swap.

## Sites fixed (2026-07-26)

- `Microsoft.ReportViewer.DataVisualization/Microsoft.Reporting.Chart.WebForms.Utilities/ImageLoader.cs`
- `Microsoft.ReportViewer.DataVisualization/Microsoft.Reporting.Gauge.WebForms/ImageLoader.cs`
- `Microsoft.ReportViewer.DataVisualization/Microsoft.Reporting.Map.WebForms/ImageLoader.cs`

All three had the identical pattern: `image = Image.FromStream(WebRequest.Create(uri).GetResponse().GetResponseStream());`. Converted to a shared `static readonly HttpClient`, `HttpClient.Send(...)` (a genuine synchronous API since .NET 5 — no async propagation needed), and the response body buffered into a `MemoryStream` before calling `Image.FromStream`. The buffering step matters: `Image.FromStream` requires its backing stream to stay open for the image's lifetime (a documented GDI+ gotcha), which is exactly why the original code never disposed the network response/stream. Disposing the `HttpResponseMessage` right after decoding — the naive one-line translation — would have reintroduced a real bug (the image throwing once its backing stream closes). Buffering into a `MemoryStream` first lets the network response be disposed cleanly while the image keeps a safe, undisposed in-memory backing store, which is strictly better than the original (no leaked live socket).

- `Microsoft.ReportViewer.Common/Microsoft.ReportingServices.Diagnostics/ExternalResourceLoader.cs` (2026-07-26) — this was the site originally scoped as "a real redesign, not just the simple GET case" (file:// handling, impersonation/credentials, hand-rolled abort polling); turned out tractable as a single self-contained rewrite once picked up:
  - `file://` URIs now go through `File.OpenRead` directly (no `HttpClient` involved at all), sidestepping `FileWebRequest`'s removal entirely.
  - `http(s)://` URIs use a per-call `HttpClient`/`HttpClientHandler` pair — a new one per call (not a shared static instance) because credentials are genuinely per-call here (`NetworkCredential`/`CredentialCache.DefaultCredentials`/anonymous), matching the original per-request `WebRequest.Credentials` semantics; this is a low-volume external-resource-fetch path, not a hot loop, so the allocation cost is a non-issue.
  - The request timeout (`webRequest.Timeout`) became a `CancellationTokenSource(timeoutMs)`, passed to `HttpClient.Send(request, cts.Token)` (the genuine synchronous send API, same as the `ImageLoader.cs` sites) and to `HttpContent.ReadAsStream(cancellationToken)`.
  - The `BeginGetResponse`/1s-polling/`Abort()` loop (`ExternalResourceAbortHelper`) has no `HttpClient` equivalent (no in-flight abort primitive) — replaced with a `System.Threading.Timer` that polls `abortHelper.IsAborted` every second and calls `cts.Cancel()` on the *same* token already bounding the request, so both the hard timeout and the abort helper cancel through one mechanism. Note: `System.Threading.Timer` had to be fully qualified — this file's namespace (`Microsoft.ReportingServices.Diagnostics`) already declares its own unrelated `Timer` class, an `error CS1729`-then-`CS0104`-style collision caught immediately at build.
  - Exception-type change (documented, not fixed): timeout/abort now throws `TaskCanceledException` instead of `WebException` with `WebExceptionStatus.Timeout`; non-2xx responses now throw `HttpRequestException` (via `EnsureSuccessStatusCode()`) instead of `WebException` with `WebExceptionStatus.ProtocolError`. The sole caller (`Microsoft.Reporting/GetResourceForLocalService.cs`) doesn't catch either exception type specifically (a bare `try/finally`), so this is a pure pass-through change, not a behavior regression at the one real call site — but any *other* future caller relying on `WebException` specifically would need updating.
  - New `ExternalResourceLoaderTests.cs` (5 tests) exercises this for real against an in-process `HttpListener` loopback server (GET success + `Content-Type` passthrough, `maxResourceSizeBytes` truncation, an already-aborted `ExternalResourceAbortHelper` throwing `TaskCanceledException` before a deliberately slow response completes) plus the `file://` branch and `IsValidResourceSize`. Verified: `dotnet build --no-incremental` 0 errors (2 fewer `SYSLIB0014` warnings, 5840 vs. 5842), `Chart.Rdl.Tests` 105/105 (100 + 5), `ReportViewerCore.LinuxRenderers.Tests` 15/15, 0 regressions.
