# XmlValidatingReader → XmlReader+XmlReaderSettings migration (CS0618)

**Status: DONE (2026-07-27).** `Microsoft.ReportingServices.ReportProcessing.RDLValidatingReader` no longer derives from `XmlValidatingReader`; see "How it was fixed" below.

## Scope (as originally found)

`Microsoft.ReportViewer.Common/Microsoft.ReportingServices.ReportProcessing/RDLValidatingReader.cs` derived from `XmlValidatingReader` (obsolete, CS0618: "Use XmlReader created by XmlReader.Create() method using appropriate XmlReaderSettings instead"). Its subclass — a `RmlValidatingReader` nested inside `Microsoft.ReportingServices.ReportProcessing.ReportPublishing` (in `ReportPublishing.cs`, confusingly the same class/file name as an unrelated pair of types in the `Microsoft.ReportingServices.ReportPublishing` namespace — see "A naming trap worth remembering" below) — is the active RDL schema validator used every time any report definition is loaded: `ReportProcessing.CreateIntermediateFormat` → `ReportPublishing.Phase1` constructs it via `RmlValidatingReader.CreateReader(...)` and drives the entire report-definition parse through `while (m_reader.Read())`. This runs against untrusted report XML, so correctness here is security-relevant, not just a style concern.

## How it was fixed

Rewrote `RDLValidatingReader` from `: XmlValidatingReader` to `: XmlReader` (composition instead of inheritance), directly mirroring an already-existing sibling class — `Microsoft.ReportingServices.ReportPublishing.RDLValidatingReader` (a *different* class, despite the identical name) had already been through this exact migration at some earlier point, wrapping an inner `XmlReader` and forwarding every abstract member. That sibling's constructor builds its validating `XmlReader.Create(stream, settings)` eagerly, in one shot, because its one caller (`RmlValidatingReader.cs`'s standalone class) passes a complete schema map up front.

This class's real subclass (the nested `RmlValidatingReader`) doesn't do that — it calls `base(textReader, targetRDLNamespace)` first, then mutates `base.Schemas.Add(...)`, `base.ValidationEventHandler += ...`, and `base.ValidationType = ...` *afterward*, all before the first `Read()`. `XmlValidatingReader` tolerated this because it was driven lazily node-by-node with no fixed "build" step; `XmlReader.Create(reader, settings)` has no equivalent — once created, the validating reader's settings are fixed. So the new class defers building the real validating `XmlReader` until first actual use (a `Reader` property backed by `m_reader ?? (m_reader = XmlReader.Create(m_innerReader, m_settings))`), letting `Schemas`/`ValidationEventHandler`/`ValidationType` stay mutable via a held `XmlReaderSettings` right up until that point — by which time the subclass constructor has already finished mutating them.

Every other member (`Validate(out message)`, `TraverseParticle`, the `RdlElementStack`/`XmlNullResolver` nested helpers, all forwarded `XmlReader` abstract members) is a mechanical port of the original body with `base.X` replaced by `Reader.X`, plus one real behavior fix: `base.SchemaType as XmlSchemaComplexType` (old `XmlValidatingReader.SchemaType`, safe even with no schema info) became `Reader.SchemaInfo?.SchemaType as XmlSchemaComplexType` — the `?.` matters, since `XmlReader.SchemaInfo` is `null` unless schema validation actually produced info for the current node, and the sibling class's own equivalent line (`m_reader.SchemaInfo.SchemaType`, no `?.`) skips that check; not copied here since it would be a latent null-ref waiting to happen, not a proven-safe pattern.

The nested `RmlValidatingReader` subclass itself needed **zero changes** — every member it calls on `base` (`Schemas`, the `ValidationEventHandler` event, `ValidationType`, `Read()`, `Validate(...)`, `EOF`, `NodeType`, `NamespaceURI`, `IsEmptyElement`) already existed with the same name/shape on the new class; `Skip()`/`ReadString()`/`ReadInnerXml()` are non-abstract virtuals on `XmlReader` itself with default implementations that work correctly through virtual dispatch once the core abstract members are properly forwarded.

### A naming trap worth remembering

There are **three** distinct RDL-validation-adjacent classes that are easy to conflate:
1. `Microsoft.ReportingServices.ReportProcessing.RDLValidatingReader` (this file) + its nested `RmlValidatingReader` subclass (in `Microsoft.ReportingServices.ReportProcessing.ReportPublishing`, itself in a file called `ReportPublishing.cs`) — the one migrated here, and the one on the live `LoadReportDefinition` path.
2. `Microsoft.ReportingServices.ReportPublishing.RDLValidatingReader` (different namespace, different file, already `XmlReader`-based) + its own standalone subclass `Microsoft.ReportingServices.ReportPublishing.RmlValidatingReader` (also its own file) — a *separate* implementation used by the report-*publishing*-to-server path, not report loading. Out of scope, never needed fixing.
3. `Microsoft.ReportingServices.ReportProcessing.RdlValidator` (no "ing" — different name entirely) — a third, already-modern, composition-based validator used by `RdlObjectModel.Serialization/RdlReader.cs`, an unrelated serialization path.

If a future session needs to touch RDL validation again: confirm which of these three is actually on the call path in question before assuming a fix in one covers the others — they look alike but are genuinely independent implementations.

## Verification (2026-07-27)

`dotnet build --no-incremental`: 0 errors; the CS0618 warning for this file is gone (the 4 remaining CS0618 warnings in the full build are unrelated `SKRunBuffer.GetGlyphSpan()`/`SKPositionedRunBuffer.GetPositionSpan()` Skia API deprecations in `SkiaTextRunRasterizer.cs`). `Chart.Rdl.Tests` 171/171 on Windows — meaningful here specifically because every one of those tests loads a real RDLC report definition through this exact validator. Also run under WSL: 163/171, the same 8 pre-existing environment-only failures documented in `docs/build-and-test.md` (Windows-only font paths, one legacy GDI+ baseline test) and zero new failures — confirms the rewrite has no platform-specific behavior gap either, even though the class itself only uses portable BCL `XmlReader`/`XmlSchema` APIs with no P/Invoke.

## Why this was deferred rather than fixed during the original warning sweep

`RDLValidatingReader`/`RmlValidatingReader` used inheritance (`: XmlValidatingReader`) and relied on members with no direct `XmlReader` equivalent (`base.SchemaType`, `base.Schemas`, `base.ValidationEventHandler`/`base.ValidationType` needing to move to a settings object set before `XmlReader.Create`) — a from-scratch redesign of the class shape (inheritance → wrapping), not a call-by-call swap, and one sitting directly in the path that validates report XML before processing. Worth doing carefully and in isolation, which is exactly what happened above once picked back up.
