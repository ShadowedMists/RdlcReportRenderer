# Chart/Gauge default-Font cross-platform gap

**Status: DONE (2026-07-31).** A real, complex chart (Sunburst — nested rings, per-node labels, a Legend) now renders end-to-end on Linux via IMAGE/PNG output, WSL-verified with a fully-rendered correct output image (2.928% pixel difference from the Windows baseline, almost certainly benign font-rendering/anti-aliasing variance). See "Chase complete (2026-07-31)" below for the full 6-fix chase that got there, spanning the Chart engine's own default-Font handling (this file's original scope) through several further gaps found by iterating past it (`GraphicsPath` construction, `MapAreasCollection`'s hot-region path-splitting, and finally a completely different subsystem, the IMAGE-format page renderer's own screen-DPI query).

## Legend fix (done, 2026-07-28)

Ported `Legend`'s and `LegendCell`'s auto-fit-sizing font construction from `System.Drawing.Font` to `IChartFont` (`IDrawingResourceFactory.CreateFont`/`WrapFont`, which already existed and never touch `System.Drawing.Font`):
- `Legend.autofitFont`'s type changed from `Font` to `IChartFont`. Added `GetBaseFontResource(chartGraph)` (returns `WrapFont(font)` if a real Font was explicitly set, else `CreateFont(ChartPicture.GetDefaultFontFamilyName(), 8f)` directly — never touching the concrete `Font` property, whose getter would otherwise construct one) and `ResizeFontResource(chartGraph, baseFont, newSize)` (builds a resized `IChartFont` via `CreateFont` using the *current* `IChartFont`'s own `FontFamilyName`/`Style`/`Unit`, never re-reading the concrete `Font` property). Added the same pair for the separate bold Title-text font (`GetTitleFontResource`).
- **Found three separate `MeasureStringAbs("W"/"WW", Font)` call sites, not just the one in `GetOptimalSize` originally traced** — `RecalcLegendInfo`, `GetOptimalSize` (its own top, before the auto-fit loop), and `CheckLegendItemsFit` all had their own independent pair. Missing any one of them still crashes the whole render — this is worth remembering when porting `Axis`: grep for *every* occurrence of the pattern in the class, don't trust a single method's read to be exhaustive.
- `LegendCell.SetCellPosition`/`MeasureCell`/`Paint`/`PaintCellText`/`PaintCellImage`/`PaintCellSeriesSymbol`'s `Font legendAutoFont` parameter became `IChartFont legendAutoFont`. `GetCellFont` (used by both `MeasureCell` and `PaintCellText`) now returns `IChartFont`, resizing via `CreateFont` when a per-cell/per-column font override needs shrinking, or `WrapFont` when using an override as-is (importantly: **not** disposed by the caller in the wrap-without-resize case, since `GdiChartFont.Dispose()` disposes the underlying `Font` too, and that `Font` is owned by the user/caller, not by this code — only the genuinely-new resized `CreateFont` result gets `disposeFont = true`).
- **Verified thoroughly**: all 137 `VisualRegressionTests` + 187 `Chart.Rdl.Tests` still pass on Windows with byte-identical pixel baselines (the `WrapFont`/`CreateFont` round-trip through Gdi's adapter produces the exact same rendering as the original raw `new Font(...)` calls). Under WSL, confirmed the crash in `SimpleBarChart_RendersViaSkia_MatchesBaseline` moved *past* `Legend.GetOptimalSize`/`Legend.get_Font()` entirely, landing in `Axis.Resize` → `Label.get_Font()` instead — direct proof the Legend path is now genuinely fixed, not just superficially patched.
- **Aggregate `VisualRegressionTests` pass count did not move yet (still 30/137)** — expected, since virtually every real chart scene has *both* a Legend and an Axis, and Axis's own equivalent gap (below) is hit immediately after Legend's is cleared. This is still real, necessary, independently-verified progress, not wasted effort — multi-blocker migrations often don't show aggregate movement until the last blocker in a chain clears.

## What this covers

`Microsoft.Reporting.Chart.WebForms`/`Microsoft.Reporting.Gauge.WebForms`'s model classes (`Title`, `Legend`, `Axis`, `Series`/`DataPointAttributes`, `Annotation`, `FinancialMarker`, `LegendCellColumn`, `StripLine`, `ChartPicture`; Gauge's `CustomLabel`, `GaugeLabel`, `LinearLabelStyle`, `LinearPinLabel`, `NumericIndicator`, `State`, `StateIndicator`) each expose a public `Font` property with a sensible default value (e.g. "Microsoft Sans Serif, 8pt") for when the report/user code never explicitly sets one.

## Current state

**Fixed (2026-07-28):** every one of these classes used to construct its default `Font` **eagerly**, in a field initializer (`private Font font = new Font(...)`) — meaning simply constructing a `Chart`/`Legend`/`Axis`/etc. object crashed immediately on Linux, since `System.Drawing.Font` construction requires GDI+, which cannot construct anything at all on Linux under .NET 10 (even with `libgdiplus` installed — the Phase 0 spike finding, `docs/platform-support.md`). All of the above were converted to lazy backing fields (`private Font font;` + `return font ??= new Font(...)` in the getter), so building the object graph itself no longer touches GDI+ unless something actually reads `.Font`.

**Still open:** GDI+ cannot construct `Font`/`FontFamily` **at all** on Linux, lazily or not — so the FIRST time any code path actually needs a live default `Font` instance (not a user-supplied one), it still crashes. Confirmed via `Legend.GetOptimalSize` → `Legend.Font`'s getter, reached from `ChartPicture.Paint`→`Resize`→`CalcLegendPosition`→`LegendCollection.CalcLegendPosition` — i.e., **any chart with a Legend still fails to render on Linux**, not at construction time anymore, but at layout/measurement time. `VisualRegressionTests` improved from 29/137 to only 30/137 passing after the construction-time fix — most remaining failures now hit this same wall.

## Why this is a different, harder problem than the construction-time bug

The construction-time bug was fixable with laziness alone, because nothing actually *needed* the Font value merely to exist as an object graph. The measurement-time problem is different: `Legend.GetOptimalSize` calls `chartGraph.MeasureStringAbs("W", Font)`, which bridges via `resourceFactory.WrapFont(font)` (`ChartGraphics.cs`) to the already-correct, Skia-safe `MeasureStringAbs(string, IChartFont)` overload — so the *measurement infrastructure itself* is fully migrated and correct. The problem is one step earlier: `WrapFont` needs an actual `System.Drawing.Font` instance to wrap, and constructing that instance (even just to read its `.FontFamily.Name`/`.Size`/`.Style` so a portable `IChartFont` could be built instead) is exactly the operation that's permanently impossible on Linux.

## Proposed fix — revised and deepened after reading `Legend.GetOptimalSize` in full (2026-07-28)

**The original scoping above (this section, prior to this update) underestimated the problem.** It assumed the only issue was a one-time measurement call (`MeasureStringAbs("W", Font)`) that could be routed around by detecting "was Font ever explicitly set." Reading `GetOptimalSize` in full shows the real blocker is deeper and *unconditional*: immediately after the first measurement calls, line `autofitFont = new Font(Font, Font.Style);` runs **whenever `legendItems.Count > 0`**, regardless of whether `AutoFitText` is even enabled, regardless of whether the user explicitly set a `Font`. Then, inside the auto-fit loop (only when `AutoFitText` is on), it constructs *another* new `Font` at a smaller size on every iteration: `autofitFont = new Font(Font.FontFamily, num2, Font.Style, Font.Unit);` — repeatedly, to find a size that fits.

This means the real, pervasive pattern isn't "a default Font was never set" — it's that **Legend's whole auto-fit-sizing mechanism is built around constructing new `System.Drawing.Font` instances at computed sizes**, as its core operating technique, for *any* legend with content, default or user-supplied font alike. The "was it explicitly set" distinction from the original scoping doesn't help here: even a user-supplied `Font` gets re-constructed at a new size for auto-fit, and that re-construction is exactly what's impossible on Linux.

**Grep confirms the same pattern recurs elsewhere** — `Axis.cs` has multiple `autoLabelFont = new Font(base.LabelStyle.Font.FontFamily, ..., base.LabelStyle.Font.Style, GraphicsUnit.Point)` sites (axis label auto-fit, the same shape as Legend's), and likely other auto-fit-adjacent code not yet inventoried (`ChartArea.cs:1626` does the same for `AxisX.autoLabelFont`).

### What a real fix looks like

This is not a call-site patch — it's a genuine port of the "compute an auto-fit font at a candidate size" operation from constructing `System.Drawing.Font` to constructing `IChartFont` (via `IDrawingResourceFactory.CreateFont(familyName, size, style, unit)`, which already exists and already builds a Skia-native font with no `System.Drawing.Font` involved at all). Concretely, for `Legend` (and the same shape for `Axis`):
1. Change `autofitFont`'s type (or add a parallel field) from `Font` to `IChartFont`, and change every construction site (`new Font(Font, Font.Style)`, `new Font(Font.FontFamily, num2, Font.Style, Font.Unit)`) to `chartGraph.ResourceFactory.CreateFont(...)`, reading `FontFamily.Name`/`Style`/`Unit` as plain data once (this one read of the *base* `Font` — not a resize — is the only place a real `System.Drawing.Font` construction is still needed, and only when a non-default value was actually set; the default-family-name case can skip the concrete `Font` entirely by using `ChartPicture.GetDefaultFontFamilyName()` directly).
2. `MeasureStringAbs` already has an `IChartFont`-taking overload (`ChartGraphics.cs`) — switch the measurement calls to use it with the new `IChartFont`-typed `autofitFont` instead of the concrete `Font`.
3. Whatever eventually *draws* using `autofitFont` (not yet traced — likely `LegendItem`/`LegendCell` drawing code) needs to accept `IChartFont` too, or the dual-overload bridge pattern already established for the rest of Chart (`docs/rendering-abstractions.md`'s "dual-overload strategy") needs to apply here as well.
4. This is real, non-trivial work in the same spirit as the original Chart/Gauge GDI+→interface migration (which took multiple sessions/milestones) — **not a quick fix**, and shouldn't be rushed as a single autonomous-loop increment. Whoever picks this up next should budget for tracing the full `autofitFont`/drawing call chain before touching code, the same way the original Milestone A/B/C Chart migration did.

## Related, deliberately not fixed this pass

`DynamicImageInstance.GetImage`'s exception handler falls back to `CreateExceptionImage`, which is itself 100% GDI+ (`new Bitmap`, `Graphics.FromImage`, `Pen`/`Brush`/`Font`) and silently fails the same way on Linux (own inner catch swallows the failure, returns `null`). This is why a chart/gauge that fails to render on Linux today produces a *silently blank* space rather than any visible error or exception — worth knowing when debugging, not fixed here since it's a defensive fallback path working as designed everywhere except this platform.

**Why this is a genuinely different location, not just the same Legend gap rediscovered:** everything else in this file (Legend/Axis fixes, the `autofitFont` proposed-fix section) lives inside `Microsoft.Reporting.Chart.WebForms` — the vendored Chart engine's own rendering internals, reachable only once a `Chart`/`Legend`/`Axis` object already exists and something tries to *render* it. `MapperBase`/`ChartMapper` live in `Microsoft.ReportViewer.Common`'s `OnDemandReportRendering` namespace — a completely separate layer, one level *above* the Chart engine, responsible for translating RDL `<Chart>`/`<ChartLegend>` XML definitions into the Chart engine's own object model (setting `chartLegend.Font` from RDL style info) *before* the Chart engine ever runs `RenderChart`/`Paint`. `MapperBase.FontCache` is `ChartMapper`'s (and presumably `GaugeMapper`'s/`MapMapper`'s, since `FontCache` lives on the shared `MapperBase`) own font-construction/caching utility, entirely unaware of `IChartFont`/`IDrawingResourceFactory` — it just calls `new Font(familyName, size, fontStyle)` directly, unconditionally, the same way `Legend.autofitFont`'s original eager field initializer did before this file's Legend fix.

**Same permanent wall, same proposed-fix shape, not fixed here.** Per this file's own "Why this is a different, harder problem than the construction-time bug" and "What a real fix looks like" sections above: `System.Drawing.Font` construction is impossible on Linux under .NET 10 full stop, lazy or not, `libgdiplus` installed or not. The only real fix is routing `MapperBase.FontCache`'s callers through `IDrawingResourceFactory.CreateFont(...)` instead of `new Font(...)` — but `FontCache` returns plain `System.Drawing.Font` values that get assigned directly onto the Chart engine's own model properties (e.g. `chartLegend.Font`), which are themselves typed as concrete `Font` (by design, per this whole session's "bridge-at-sink"/`WrapFont` convention — model properties stay concrete, only rendering-time code becomes interface-typed). Making `MapperBase.FontCache` produce something other than a `System.Drawing.Font` would mean either widening the Chart engine's own public model surface (a bigger, cross-cutting change well beyond this file's scope) or finding some other indirection — **not scoped or attempted this pass**, consistent with this file's existing guidance not to rush a fix here.

**Practical implication:** *any* RDL report with a Chart/Gauge/Map Legend (or anything else that flows through `MapperBase.GetDefaultFont()`/`FontCache.GetFont()` during RDL-to-model mapping) will fail to render into IMAGE/PNG output on Linux — not because of anything in the Chart engine's rendering internals (all fixed this session), but because the mapping layer that builds the chart's model in the first place can't construct a `Font` value to assign. This is very likely the actual root cause of `tasks/image-renderer-cross-platform.md`'s "Chart/Gauge/Map embedding" remaining gap (that doc pointed here already, but only speculatively — this WSL trace confirms and narrows it down to this exact call chain).

## Update (2026-07-31): the Chart-only mapper fix, done, plus an iterative chase through 3 more real bugs

Contrary to the "not scoped or attempted this pass" note directly above (written before a closer trace), the practical fix turned out to be smaller and safer than "widen the model's `Font` properties": **`MapperBase.FontCache.GetFont`/`GetFontFromCache` now catch the platform-construction failure and return `null` instead of throwing**, and `ChartMapper.cs`'s ~6 Legend/Axis/Title/StripLine/DataPointAttributes call sites skip the property assignment on `null` rather than assigning it (important because e.g. `Legend.Font`'s setter has a side effect, `AutoFitText = false`, that must not fire for a font that was never actually resolved). Also added `FontCache.DefaultFontFamily` (a string-only accessor, never constructs a `Font`) to replace two internal call sites that were reading `GetDefaultFont().Name` purely for a fallback family-name string — constructing a `Font` just to read its name back was itself part of the same crash. This is genuinely single-session-sized and done — see commit `8585321`.

**This opened up an iterative "fix it, WSL-verify, find the next blocker" chase** (matching the pattern already used successfully for the WORD-binary CFBF fix), using temporary `Console.Error.WriteLine` diagnostics in `ChartMapper.cs`'s `RenderChart`/`GetImage` catch blocks (added and reverted each round, never committed) to surface the real exception, since `DynamicImageInstance.GetImage`'s own catch-and-placeholder silently swallows it. Each round re-ran `SunburstChartRdlTests.SunburstChartWithCategoryHierarchy_MatchesBaseline` under WSL and viewed the actual output PNG directly (not just the pass/fail assertion) to check for real progress:

1. **Round 1** (the mapper fix above): crash moved from `FontCache.CreateSafeFont` to a new site.
2. **Round 2**: `Legend.AutoFitText`'s property setter (`Legend.cs:309-333`, defaults to `true`) unconditionally constructs a real `Font` to seed the starting auto-fit size (either resizing an existing font to 8pt, or building `ChartPicture.GetDefaultFontFamilyName()` from scratch). ## Chase complete (2026-07-31): SunburstChart renders end-to-end on Linux

After round 6, a rigorous re-verification (deleting the existing output PNG first, re-running under WSL, and confirming via file listing that a *fresh* PNG was actually written this time — not a stale leftover from an earlier successful run, which had caused one false-positive read earlier in this chase) showed `SunburstChartWithCategoryHierarchy_MatchesBaseline` **failing only on pixel-tolerance grounds**: 4250 of 145152 pixels (2.928%) differ, down from complete blankness.
