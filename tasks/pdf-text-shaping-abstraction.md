# RichText text-shaping cross-platform abstraction (PDF's real blocker)

**Status (2026-07-26): a real, working cross-platform PDF text MVP is done for simple (single-style) text boxes — via a different, smaller approach than originally planned below.** This supersedes the "P4" line item in `pdf-render-callstack-analysis.md`/`pdf-quick-reference.md`. See "MVP: base-14 fonts, done" below before reading the original phased plan — the plan was written assuming a full Skia/HarfBuzzSharp shaping port was the only way forward; a further trace found a much smaller path that ships real functionality now.

**P4 progress (2026-07-26): the shaping/itemization/line-break prototypes are now wired into PDFWriter's cross-platform text path, for measurement only - not for drawing.** `DrawWrappedText`/`DrawWrappedRichText` now decide word-wrap points and decoration-rectangle widths using real shaped glyph widths and soft-break opportunities (`ShapedTextMetrics`/`ShapedTextWrapper`/`ShapedStyledTextWrapper`, `Microsoft.ReportingServices.Rendering.ImageRenderer/ShapedTextLayout.cs`) instead of the MVP's per-character-class approximation table. Drawing itself is unchanged: still base-14 fonts via plain-text `Tj`, since real font embedding remains deferred (see `docs/decisions.md`). This does NOT touch the RichText/Uniscribe production pipeline (`FontCache`/`TextRun`/`LineBreaker`/`Paragraph` still exclusively Win32) - that remains the real, not-yet-attempted "full fidelity" wiring described in "Recommended phased plan" below.

## MVP: base-14 fonts + approximate word-wrap (done 2026-07-26)

Tracing `PDFWriter`'s own "P3" font-metrics call sites (`ProcessDrawStringFont`/`WriteFont`/`WriteEmbeddedFont`/`ProcessFontForFontEmbedding`) down to their actual inputs found they were never independently reachable: `run.CachedFont.Font`/`.Hfont`/`.TextMetric` all come from a live `RichText.CachedFont`, constructed by the RichText pipeline *before* `PDFWriter.DrawTextRun` is ever invoked (it's a callback from inside `TextBox.Render`). So "P3 is bounded, independent of P4" (the original 2026-07-24 scoping) was itself wrong — P3's call sites are only reachable through P4's blocked pipeline. There is no way to reach them on Linux at all, regardless of how portable PDFWriter's own code is.

The unlock: PDF's standard 14 fonts (Helvetica/Times/Courier families) need **no** embedded font data and **no** `/Widths` array — real PDF readers already know their metrics natively (`WriteFont`'s existing `InternalFont` branch confirms this: it emits only `/Subtype /Type1 /BaseFont /Helvetica /Encoding /WinAnsiEncoding`, nothing else). `PDFWriter.cs`'s existing `m_internalFonts` dictionary already maps common Windows family names (`"Arial"`, `"Times New Roman"`, `"Courier New"`, with `,Bold`/`,Italic`/`,BoldItalic` suffixes) to these base-14 names - the exact same map `ProcessDrawStringFont` uses for its own fast path. And since the PDF reader lays out `Tj` text itself using the font's real metrics, `PDFWriter` never needs pixel/point-exact glyph widths for *positioning* - only an approximate width for its *own* word-wrap decisions (where imprecision costs a slightly early/late line break, not a spec violation).

This adds up to a real, if reduced-fidelity, path requiring **zero** GDI+/Win32/RichText/SkiaSharp/HarfBuzzSharp dependency:

- `CrossPlatformTextLayout.cs`: `ApproximateTextMetrics` (rough per-character-class em-width table) and `SimpleTextWrapper` (greedy word-wrap on explicit line breaks + spaces).
- `WriterBase.DrawWrappedText(RectangleF, PointF, string, ITextRunProps)`: new virtual hook, no-op by default (`ImageWriter`/EMF path unaffected).
- `PDFWriter.GetOrCreateBase14Font`/`DrawWrappedText`: resolves family/bold/italic to a base-14 font via the existing `m_internalFonts` map (unknown families fall back to the Helvetica family), reuses `WriteFont`/`ProcessFontForFontEmbedding`'s existing `m_fonts`/`ReserveObjectId`/`m_fontsUsedInCurrentPage` bookkeeping so the synthetic `PDFFont` (constructed with `CachedFont: null`, `InternalFont: true`, `IsComposite: false`) gets written out by the *existing, unmodified* font-dictionary code - which already short-circuits before touching `CachedFont`/HDC for that combination (verified by reading both methods). Emits `BT/Tf/color/Td/Tj/T*/ET` directly via `WriteText(null, ...)`, which was confirmed by reading `WriteText`/`MapGlyphToUnicodeChar` to never dereference its `TextRun` parameter on the `InternalFont`-non-composite branch.
- `Renderer.ProcessSimpleTextBox`: branches on `!OperatingSystem.IsWindows()` to call `Writer.DrawWrappedText(...)` instead of constructing `RichText.Paragraph`/`TextBox`/calling `richTextBox.ScriptItemize()`/`LineBreaker.Flow`/`TextBox.Render` at all. `ProcessRichTextBox` (multi-run rich text) is unchanged - a documented next-increment gap, below.

**Verified (2026-07-26):** built and ran a minimal RDLC (`tests/Microsoft.ReportViewer.Chart.Rdl.Tests/Reports/SimpleTextboxReport.rdlc`) with the cross-platform branch temporarily forced (a one-line, reverted-after-verification edit to `ProcessSimpleTextBox`'s condition) and rendered it to PDF with `HumanReadablePdf=true`; the output PDF opened correctly with the expected text, correctly word-wrapped at the textbox width, in Helvetica. Also added a permanent test (`SimpleTextboxRdlTests.SimpleTextbox_RendersToPdf_ContainsExpectedText`, using the same report) that runs the *Windows* path (this dev environment can't run Linux directly) and asserts the PDF is well-formed and contains the expected text - full test suite passing (155 tests) with zero behavior change on Windows.

**Extended to rich (multi-run) text boxes (2026-07-26, same day):** `Renderer.ProcessRichTextBox` now has the same platform branch, calling a new `WriterBase.DrawWrappedRichText`/`PDFWriter` implementation. `StyledTextWrapper.WrapParagraph` (`CrossPlatformTextLayout.cs`) word-wraps a paragraph's runs *across* run boundaries (a run can split mid-word-wrap the same as plain text), merging adjacent same-style fragments; each paragraph is wrapped independently so paragraph breaks are preserved as forced line breaks. Drawing relies on the PDF reader's own post-`Tj` text-position advance (driven by the *actual* font metrics for whichever base-14 font is current) to place successive same-line fragments, so `PDFWriter` never computes per-fragment x-positions itself - only `Tf`/color changes between fragments. All runs in a text box share one line-height/baseline sized to the box's largest font (documented approximation for badly mixed sizes, not exact per-run baseline alignment). Verified the same way as the simple case: forced the branch locally, rendered a report with a bold-prefix + normal-suffix run pair (word-wrapped correctly across the run boundary) plus a second, separately-styled italic paragraph, confirmed correct in the rendered PDF, reverted. Permanent test: `RichTextboxRdlTests.RichTextbox_RendersToPdf_ContainsExpectedText` (runs the Windows path, same automated-testing-gap caveat as `SimpleTextboxRdlTests`). Full suite: 156 tests passing.

**Extended with center/right text alignment (2026-07-26, same day):** both `DrawWrappedText` and `DrawWrappedRichText` now take a resolved `RPLFormat.TextAlignments` (resolved from `RPLFormat.TextAlignments.General` against the text box's `DefaultAlignment`/`Direction` by a new `Renderer.ResolveTextAlignment` helper, mirroring `RichText.TextBox.RenderParagraph`'s identical resolution). Each wrapped line's approximate width (the same `ApproximateTextMetrics` used for word-wrap) determines that line's start-x for center/right; line-to-line movement switched from `TL`/`T*` to an explicit relative `Td (dx, dy)` per line, since different lines can need different start-x under center/right alignment (a fixed `TL` leading only supports a single shared x). This was deliberately deferred in the original MVP ("an unverified per-line-position scheme was judged riskier...") but proved straightforward once implemented, since it only affects the *start* x of each already-wrapped line - drawing within a line is still handled by the PDF reader's own per-fragment advance. Verified the same way (forced locally, rendered a centered title and a right-aligned line, both visually correct in the output PDF, reverted). Permanent test: `AlignedTextboxRdlTests`. Full suite: 157 tests passing.

**Extended with underline/strikethrough (2026-07-26, same day):** `ITextRunProps.TextDecoration` (`RPLFormat.TextDecorations`: None/Underline/Overline/LineThrough - a single value per run, not flags) is now read on both paths. PDF text objects (`BT`...`ET`) may only contain text-showing/text-state operators - path-painting operators like `re f` are not legal inside one - so decorations can't be emitted inline with the `Tj` calls. Instead, a new `PDFWriter.AppendDecorationRectangle` helper builds a separate content-stream fragment (filled rectangle, same `WriteColor`/`WriteRectangle`/`re f` pattern `FillRectangle` already uses elsewhere in this file) appended as a second `m_pageContentsSection` entry right after the `BT`...`ET` block, so it's drawn on top of the text it decorates. `DrawWrappedText` computes one rectangle per wrapped line (whole-line decoration, since the box has one style); `DrawWrappedRichText` computes one rectangle per styled fragment, tracking each fragment's start-x by accumulating `ApproximateTextMetrics` widths itself (the PDF reader's own post-`Tj` advance still positions the actual glyphs; this running estimate is only used to size/place the decoration rectangle, so the same approximate-width caveat as word-wrap applies - a slight over/under-run in rare cases, not a correctness risk). Underline sits `0.15em` below baseline, strikethrough `0.3em` above (roughly text mid-height); both `~0.06em` thick, minimum `0.5pt`. Overline is not handled (not requested; a one-line addition to `AppendDecorationRectangle`'s switch if needed later). Verified the same way as prior increments: forced the cross-platform branch locally, rendered a report with a whole-line-underlined textbox, a whole-line-strikethrough textbox, and a rich-text box mixing plain/underlined/struck-through runs in one paragraph - all four decorations landed correctly positioned in the output PDF, reverted. Permanent test: `DecorationRdlTests`. Full suite: 158 tests passing.

**Known gaps in this MVP, honestly scoped rather than silently missing:**
- **Font family is not honored beyond the base-14 map** - any family not in `m_internalFonts` (i.e. not Arial/Times New Roman/Courier New/Symbol, case-sensitive, exact match) silently falls back to Helvetica. No real font embedding, no custom TrueType/OpenType fonts, no true Unicode beyond WinAnsi (`/Encoding /WinAnsiEncoding`) - matches this doc's original P4 scope note about non-ASCII text. Per user direction (2026-07-26): base-14 fonts are the deliberate stopping point for now; additional font families are explicitly deferred until after end-to-end PDF rendering is otherwise complete.
- **Word-wrap widths are approximate**, not exact glyph metrics - cosmetic imprecision only (see above), not a correctness risk, but real Adobe AFM-exact wrapping would look better. The same approximation now also sizes/places underline/strikethrough rectangles in rich text (see above).
- **No overline, no vertical/rotated text, no highlight runs** on this path - underline/strikethrough are done (above); the rest of `RPLTextBoxProps`' styling beyond family/size/bold/italic/color/decoration is not read yet.
- ~~No automated test exercises the cross-platform branch itself~~ **Resolved (2026-07-26):** `Microsoft.ReportViewer.Common/Properties/AssemblyInfo.cs` now grants `InternalsVisibleTo` to `Microsoft.ReportViewer.Chart.Rdl.Tests` - not a new trust boundary, since that test project is already signed with the same `ReportViewerCore.snk` key as `Microsoft.ReportViewer.Common` itself (verified: same `AssemblyOriginatorKeyFile` in both `.csproj`s). `CrossPlatformPdfTextTests.cs` calls `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` directly (constructing a minimal `Renderer`/`PDFWriter`/`MemoryStream` and reading the emitted content-stream operators back out) - this runs the actual cross-platform code on every platform/CI run, not just when someone manually forces the branch. It doesn't need `EndReport()` (which requires a fully-processed `RplReport` for document metadata) - `EndPage()` already flushes the page's content stream to the underlying `Stream`, which is all these tests assert on.

If this MVP needs richer fidelity later (real embedded fonts, exact metrics, arbitrary Unicode), the SkiaSharp/HarfBuzzSharp path below is still the way to get there - but it's no longer a prerequisite for "simple text boxes render on Linux," which is done.

## Real shaped-width wrapping wired into the MVP (done 2026-07-26)

The MVP above wrapped/measured text with `ApproximateTextMetrics` (a fixed per-character-class em-width table) and `SimpleTextWrapper`/`StyledTextWrapper` (split-on-space word-wrap). Once the P4 shaping/itemization/line-break prototypes existed and composed correctly (`UnicodeParagraphShaper`), they were wired into the MVP's word-wrap and decoration-sizing decisions in place of that approximation - `ShapedTextLayout.cs` (`ShapedFontCache`/`ShapedTextMetrics`/`ShapedTextWrapper`/`ShapedStyledTextWrapper`) replaced `CrossPlatformTextLayout.cs`'s approximate classes (deleted; `StyledLineFragment` is the only piece still needed and was kept). `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` now call these instead.

What changed in practice: word-wrap breaks only at real Unicode soft-break opportunities (after whitespace or a hyphen, per `UnicodeLineBreakAnalyzer`) using each run's actual shaped glyph widths (`HarfBuzzTextShaper`, via whatever font `SkiaCachedFont`/`SKTypeface.FromFamilyName` resolves for that family on the host) rather than a fixed per-character-class table. An unbreakable run of characters wider than the box is allowed to overflow rather than force a mid-word split - same fallback the approximate wrapper had, since this codebase still has no hyphenation logic.

**What did NOT change:** actual glyph drawing. `PDFWriter` still resolves the requested family to a base-14 font and emits plain-text `Tj` (not glyph-indexed `Tj`/`TJ`), relying on the PDF reader's own font metrics to lay out glyphs on the page - real font embedding using this pipeline's shaped glyph ids remains explicitly deferred (see `docs/decisions.md`'s base-14 MVP decision). This means the *wrap decisions* now use one font's real metrics while the *drawn glyphs* use whatever base-14 font a PDF reader substitutes - the same category of imprecision the approximate table always had, just measured more accurately.

Verified via `ShapedTextLayoutTests.cs` (13 tests: per-character width/break-opportunity arrays, wrap-preserves-all-characters invariants across run boundaries, no-mid-word-split behavior, explicit-newline forced breaks, same-style fragment merging) plus the existing `CrossPlatformPdfTextTests.cs` (unchanged - still passes, since it calls `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` directly and asserts on emitted operators, which this change doesn't alter the shape of). Full suite: 205 tests (137 + 53 + 15), 0 new warnings.

## Original phased plan (superseded for the simple-textbox case by the MVP above; still the path for rich text / full fidelity)

## Why this exists as its own doc

`PDFWriter` itself has no Metafile/GDI+-drawing dependency, but its one remaining hard item — Uniscribe-based text shaping — is not a bounded, RTL/CJK-only concern: it's this engine's *only* text-shaping backend, for every script, and it also constructs live GDI+ `Font` objects upstream of shaping (an independently-blocked-on-Linux wall). Full reasoning and evidence: `docs/decisions.md`'s "Correction: P4 ... understated the real scope" entry (2026-07-26).

## Blast radius (this is not PDF-scoped work)

`LineBreaker.Flow`/`TextBox.Render`/`TextBox.MeasureFullHeight` are called from:
- `Microsoft.ReportingServices.Rendering.ImageRenderer/Renderer.cs:1145,1147,1246,1250` — shared by `PDFWriter` **and** the Windows-only `ImageWriter` (EMF/TIFF) renderer.
- `RichText/RichTextRenderer.cs:1118` and `Microsoft.Reporting.WinForms/RenderingTextBox.cs:385` — the WinForms on-screen viewer's own rendering.
- `Rendering.HPBProcessing/PageContext.cs:434,444` and `Rendering.SPBProcessing/PageContext.cs:548` — the shared pagination/page-break engines used by *every* renderer, not just PDF.

`HtmlRenderer` and `ExcelRenderer` do **not** depend on this pipeline (confirmed via grep — no references to `LineBreaker`/`RichText.TextBox`). Fixing this benefits PDF, Image/EMF, the WinForms viewer, and pagination correctness together; there is no PDF-only shortcut to route around it.

## What a replacement needs to produce

`LineBreaker.Flow(TextBox, Win32DCSafeHandle hdc, float dpiX, FontCache, FlowContext, bool keepLines, out float height) : List<Paragraph>` (line-break offsets/`TextLine`s) and `TextBox.Render(...)`/`MeasureFullHeight(...)` (glyph draw + height) are the two entry points `PDFWriter`/`Renderer.cs` call. Internally they need, per run: glyph indices (`GlyphShapeData.Glyphs`), clusters, `SCRIPT_VISATTR`, advance widths (`GlyphData.Advances`/`ABC`), `GOFFSET` glyph offsets, and `SCRIPT_LOGATTR` break flags — i.e. a shaper producing glyph ids + advances + break opportunities + a bidi-reordered run list, matching the shapes already defined in `TexRunShapeData.cs`/`GlyphShapeData.cs`/`GOFFSET.cs`.

## Recommended phased plan

Given the size (this is new shaping/line-breaking logic, not a resource-type port like Chart/Gauge's migration), do not attempt this as one pass. Status (2026-07-26): steps 1-3 have working prototypes; step 4 (verification harness) is done; production wiring (step 3's real goal) has not started.

1. **Spike — done.** `tests/ReportViewerCore.LinuxRenderers.Tests/TextShapingSpikeTests.cs` proved HarfBuzzSharp can shape plain Latin text into real glyph ids + advances, with no `System.Drawing`/Win32 in the call path.
2. **Font layer — done.** `SkiaCachedFont.cs` mirrors `CachedFont`'s metrics surface (`GetHeight`/`GetAscent`/`GetDescent`/`GetLeading`, `ScaleFactor`) via `SKTypeface`/`SKFont`/`SKFontMetrics`. Scaffolding only — nothing calls it in production yet (5 tests, `SkiaCachedFontTests.cs`).
3. **Shaping layer — prototypes done, production wiring not started.** Three composable prototypes exist, each translating a Uniscribe concept into a HarfBuzz/Unicode-range equivalent:
   - `HarfBuzzTextShaper.cs`: text → `GlyphData`/`GlyphShapeData`/`ABC`/`GOFFSET` (the same shapes `TextRun.ShapeAndPlace` builds from `ScriptShape`/`ScriptPlace`), via `SkiaCachedFont.Shaper` (`SkiaSharp.HarfBuzz.SKShaper` — see `docs/decisions.md`'s `SKShaper` entry for why not a hand-rolled `HarfBuzzSharp.Face`/`Font`). 6 tests (`HarfBuzzTextShaperTests.cs`).
   - `UnicodeTextItemizer.cs`: text → script/direction runs with real `SCRIPT_ANALYSIS` values (via the existing `ScriptAnalysis`/`ScriptState` wrapper classes), using coarse Unicode code-point ranges instead of Uniscribe's script table. 7 tests (`UnicodeTextItemizerTests.cs`).
   - `UnicodeLineBreakAnalyzer.cs`: text → per-character `SCRIPT_LOGATTR` via a hand-rolled soft-break-after-whitespace-or-hyphen heuristic (not UAX #14-compliant). 6 tests (`UnicodeLineBreakAnalyzerTests.cs`).
   - `UnicodeParagraphShaper.cs` composes all three into one per-paragraph pipeline (itemize → shape each item with its slice of line-break attributes). Composing them (not just unit-testing each in isolation) surfaced a real native crash, fixed by switching to `SKShaper` — see `docs/decisions.md`. Full suite after composition: 192 tests, 0 new warnings.

   Honest scope, all four files: plain LTR non-reordering text only (Latin/Cyrillic/Greek/numbers/punctuation). `SCRIPT_VISATTR` is zeroed (unread by this codebase). No fallback-font-on-missing-glyph retry. `UnicodeTextItemizer`'s `Other` bucket (Thai/Devanagari/Hangul/etc.) is treated as LTR, which is wrong for those scripts' real shaping rules.

   **What real production wiring still needs beyond these prototypes:** (a) a platform/backend selection point inside `TextRun.ShapeAndPlace` (or a new `TextRun` subclass/strategy), (b) real Uniscribe script IDs in place of the coarse Unicode-range buckets for non-Latin scripts, (c) UAX #14 line-breaking (or an ICU4N dependency) in place of the heuristic, (d) the fallback-font/east-asian-glyph retry logic `TextRun.ShapeAndPlace` already has for Windows. Recommend scoping each as its own bounded increment — lean on the verification harness below (`ShapedTextRasterizer`/`TextRasterAssertions`) for each, since wrong cluster/line-break/reading-order bugs don't throw.
4. **Verification infrastructure — done.** Deliberately not a golden-image PNG diff (`AGENTS.md`'s Testing Philosophy prefers behavioral tests; `SKTypeface.Default` isn't guaranteed identical across hosts, and no font file is vendored in-repo to pin a reproducible baseline against). Instead, `tests/ReportViewerCore.LinuxRenderers.Tests/ShapedTextRasterizer.cs`+`TextRasterAssertions.cs` shape and rasterize text, then verify per-glyph ink lands in its shaped column and LTR advance is monotonic — checked against the shaping data that produced the raster, not a stored reference. A meta-test proves the checker has real discriminating power (deliberately corrupts a glyph position and confirms the check fails). RTL is shaped but not yet checked for correct reordering (documented gap, `TextRenderingVisualTests.cs`). Reusable once step 3's shaper is wired into production — feed its output into `TextRasterAssertions` the same way.
5. Once a Skia/HarfBuzzSharp path renders a plain-Latin PDF page correctly on both Windows and Linux (byte-identical is not the bar, same as Chart's Skia-vs-its-own-baseline precedent), revisit whether P1-P3's `GraphicsBase`/HDC-metrics call sites (`PDFWriter.cs:1343,1972,2170,2338`) need their own `SKFont`-based port or can be bypassed for the Skia-backed `CachedFont` path.
