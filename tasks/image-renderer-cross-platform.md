# IMAGE (TIFF/EMF) renderer: cross-platform support

**Status: Phases 1-3 DONE (2026-07-28)** — image decoding, a Skia-backed raster drawing surface (pens/brushes/shapes/images), and text (via `PDFWriter`'s existing shaped-text infrastructure) all work end-to-end on Linux for BMP/JPEG/PNG, WSL-verified with real rendered-and-inspected PNGs. TIFF/EMF remain permanently Windows-only (no portable equivalent). **Remaining open gap: Chart/Gauge/Map content still doesn't reach IMAGE-format output on Linux** — root-caused 2026-07-30 to a new instance of the "Font construction is impossible on Linux" wall, in the RDL-to-chart-model mapping layer rather than the Chart engine's own rendering internals (see `tasks/chart-default-font-cross-platform.md`'s "New instance found: `MapperBase.FontCache`" section) — not fixed, same larger not-yet-scoped change as the rest of that file.

## 2026-07-28 scoping finding: this is a multi-file migration, not a single surface swap

Chose "Skia, narrowed scope" (BMP/GIF/JPEG/PNG only; TIFF/EMF stay Windows-only) over an ImageSharp-based full-TIFF rewrite, since SkiaSharp is already a project dependency (used by PDF's `ShapedFontCache`/`ShapedTextWrapper` text-shaping pipeline in `PDFWriter.cs`/`ShapedTextLayout.cs`) and matches the Chart/Gauge precedent. Reading `Graphics.cs`, `GraphicsBase.cs`, `GDIPen.cs`, `GDIBrush.cs`, `GDIFont.cs`, and `ImageWriter.cs` end to end (not just `Graphics.NewPage`, which the earlier fix touched) surfaced that the raster-surface construction fixed in `Graphics.NewPage` is only one of several separate GDI+-construction points that would each independently crash on Linux per the confirmed Phase 0 finding ("GDI+ cannot construct *any* `System.Drawing` object at all on Linux, not even a bare `Font`/`Pen`/`Bitmap`" — `docs/platform-support.md`):

1. **Pens/brushes**: `ImageWriter.DrawLine`/`DrawRectangle`/`FillPolygon`/`FillRectangle` call `GDIPen.GetPen`/`GDIBrush.GetBrush` (`new Pen(color, size)` / `new SolidBrush(color)`) *before* ever reaching `Graphics`'s draw methods — these crash on Linux regardless of what `Graphics.cs` does internally.
2. **Image decoding**: `ImageWriter.GetImage` (two overloads) calls `System.Drawing.Image.FromStream(...)` directly, and `System.Drawing.Image`/`Bitmap` is used as the in-memory image representation throughout — `m_cachedImages` (`Dictionary<string, System.Drawing.Image>`), `GetDefaultImage`, `GDIImageProps`, and `Renderer.ImageResources` (static `Bitmap` resources for the "InvalidImage" placeholder). This is the same class of problem the Excel renderer already solved once via `IImageProvider`/`ImageMetadata`/`CrossPlatformImageProvider` (see `docs/rendering-abstractions.md`) — that existing abstraction is a strong candidate to extend or reuse here rather than inventing a new one.
3. **Fonts**: `GDIFont` wraps a real `System.Drawing.Font`, constructed via GDI+.
4. **Text drawing**: separate from all of the above. `ImageWriter` never overrides `WriterBase.DrawWrappedText`/`DrawWrappedRichText` (the cross-platform text hooks `PDFWriter` already implements — see `SupportsCrossPlatformRichTextPipeline`), so on non-Windows, `Renderer.ProcessSimpleTextBox`/`ProcessRichTextBox` currently fall through to no-op base-class stubs: text is silently dropped, not drawn, once the raster-surface and pen/brush/image points above are fixed. Fixing this is good news, not a dead end — `PDFWriter.DrawWrappedText`/`DrawWrappedRichText` already do real cross-platform wrapping/measurement via `ShapedTextWrapper`/`ShapedStyledTextWrapper`/`ShapedTextMetrics`/`ShapedFontCache` (`ShapedTextLayout.cs`, SkiaSharp-backed), fully reusable as-is for wrap/measure decisions; only the actual glyph-drawing calls would differ (an `SKCanvas.DrawText` call onto the new raster surface instead of PDF `Tj` operators).

**Net assessment:** this is realistically a migration on the same order of size as the Chart/Gauge Ports & Adapters work (dozens of call sites across `ImageWriter.cs`/`GDIPen.cs`/`GDIBrush.cs`/`GDIFont.cs`, plus a new text-drawing override), not a single-file surface swap — the original "Proposed tasks" item 2 below undersold it. Recommended phasing for whoever picks this up next:
- **Phase 1 (done, 2026-07-28):** image decoding, via a new `PortableImage` wrapper (`Microsoft.ReportingServices.Rendering.ImageRenderer/PortableImage.cs`) — unchanged `System.Drawing.Image` behavior on Windows, `IImageProvider`-based decode (reusing the existing Excel abstraction rather than inventing a new one) on non-Windows. `ImageWriter.GetImage`/`GetDefaultImage`/`DrawBackgroundImage`/`DrawDynamicImage`/`DrawImage` all updated. WSL-verified: `PortableImage.FromStream` decodes a real PNG with `IsGdiBacked=false` and no `gdiplus` dependency. The actual draw calls (`m_graphics.DrawImage(...)`) remain guarded to `IsGdiBacked` (Windows) only, since Phase 2's raster surface doesn't exist yet — this phase changes no Windows behavior and is not yet independently visible end to end (`ImageWriterRdlTests` still fails at the same already-documented `Graphics.NewPage` point under WSL, confirmed unchanged by this phase).
- **Phase 2 (done, 2026-07-28):** raster drawing surface + pen/brush/shape/image primitives. `Graphics.cs` now branches internally on `OperatingSystem.IsWindows()` in every method - the Windows branch is the original GDI+ code, byte-for-byte unchanged (all 185+137 existing tests still pass on Windows); the non-Windows branch draws onto an `SKBitmap`/`SKCanvas`. New non-Windows-only overloads (`DrawLine`/`DrawRectangle` take `Color`+style primitives instead of a pre-built `Pen`; `FillPolygon`/`FillRectangle` take `Color` instead of a pre-built `Brush`; a new `DrawImage(byte[] bgra32Pixels, ...)` overload draws PortableImage's already-decoded pixels) so `ImageWriter.cs`'s draw overrides stay GDI+-free on that path. **Verified for real** under WSL: a new text-free fixture (`ShapesOnlyReport.rdlc` - bordered/filled rectangle + dashed line, `ImageWriterRdlTests.ShapesOnly_RendersToPng`) renders correctly end-to-end on Linux - visually confirmed (light-blue fill, black border, red dashed line, right geometry) by writing the actual PNG bytes to disk and viewing it, not just asserting well-formed output.
  - **Narrower than originally planned:** SkiaSharp's `SKImage.Encode` only actually supports JPEG/PNG output (empirically confirmed - BMP/GIF both return null data silently). BMP/GIF/TIFF/EMF all stay Windows-only for now; requesting them on non-Windows throws a clear `NotSupportedException` instead of crashing.
  - **Real bug found and fixed along the way:** `PortableImage.FromStream` originally called `IImageProvider.LoadImage` then `IImageProvider.DecodeToBgra32` on the same stream instance - `SKCodec.Create`'s `using` disposal (inside `LoadImage`) closes the underlying stream as a side effect, so the second call threw `ObjectDisposedException`. Fixed by buffering the source bytes once and passing a fresh `MemoryStream` to each call.
  - **New gap discovered, not yet investigated:** Chart/Gauge/Map content (routed through `Renderer.ProcessDynamicImage` → `Writer.DrawDynamicImage`, not the plain `RPLImage` path `ProcessImage`/`Writer.DrawImage` uses) never reaches `ImageWriter.DrawDynamicImage` at all on Linux for IMAGE-format output - confirmed via debug instrumentation that `RPLDynamicImageProps.DynamicImageContent`/`DynamicImageContentOffset` are simply unset by the time `ProcessDynamicImage` runs, so the whole draw call is skipped (no crash, just missing content - `SunburstChartRdlTests.SunburstChartWithCategoryHierarchy_MatchesBaseline` fails on Linux with a 34% pixel diff, the chart silently absent from an otherwise-correct blank page). This is a separate, upstream gap - somewhere in the RPL measurement/chart-pre-render pipeline for the IMAGE renderer specifically (the same report renders its chart correctly via PDF and via Windows IMAGE) - not something `Graphics.cs`/`ImageWriter.cs`'s draw plumbing can fix; worth its own investigation before claiming charts render cross-platform through IMAGE format.
- **Phase 3 (done, 2026-07-28):** text. `ImageWriter` now overrides `DrawWrappedText`/`DrawWrappedRichText` (`WriterBase`'s cross-platform text hooks, previously only implemented by `PDFWriter`) - reusing `PDFWriter`'s existing `ShapedFontCache`/`ShapedTextWrapper`/`ShapedTextMetrics`/`ShapedStyledTextWrapper` infrastructure for wrapping/measurement, with a new `Graphics.DrawText` (SkiaSharp `SKCanvas.DrawText`) for the actual glyph drawing instead of PDF `Tj` operators. `ImageWriter` never overrides `SupportsCrossPlatformRichTextPipeline` (stays `false`, the default) - that alone is what makes `Renderer.ProcessSimpleTextBox`/`ProcessRichTextBox` route to `DrawWrappedText`/`DrawWrappedRichText` on non-Windows, no extra wiring needed.
  - One real seam had to be added: `ShapedStyledTextWrapper`/`ShapedTextMetrics` read `FontSize` directly off the `ITextRunProps` style object (no parameter to override it), but RDL font sizes are in points while this renderer's canvas is in device pixels - so a new `PixelScaledTextRunProps` adapter (wraps an `ITextRunProps`, scales `FontSize` by `dpi/72`, forwards everything else) bridges the two for the rich-text path. The single-style path (`DrawWrappedText`) doesn't need this - it calls `ShapedTextWrapper.Wrap` directly with an explicit pixel font size parameter.
  - **Verified for real**, not just build-verified: visually confirmed under WSL with two new fixtures - `SimpleTextboxReport.rdlc` (single-style, wraps correctly across 2 lines) and a new `RichTextProbeReport.rdlc` (bold red run + plain blue run in one center-aligned paragraph, wraps across 3 lines with per-run color/weight and correct center alignment) - by writing the actual output PNGs to disk and inspecting them, matching this repo's established verification convention.
  - All 187 Windows tests still pass (Windows text path - `ImageWriter.DrawTextRun`'s original Win32 HDC/Uniscribe pipeline - is completely untouched). The 12 pre-existing WSL failures (Word binary COM, missing TTC/CJK font files on the dev box, the Sunburst chart-embedding gap from Phase 2) are unchanged in nature and count - Phase 3 introduces no regressions.
- Each phase landed as its own small, WSL-verified commit, per this repo's established convention.

## Remaining gaps after Phases 1-3

- **Chart/Gauge/Map embedding** still doesn't reach the page on Linux for IMAGE format (the `ProcessDynamicImage`/`DynamicImageContent` gap found during Phase 2 - see above). Root-caused 2026-07-28: `DynamicImageInstance.GetImage` silently swallows the real exception and falls back to a GDI+-based `CreateExceptionImage` that *also* fails silently on Linux. **Root-caused further, 2026-07-30, via temporary diagnostic instrumentation (added and reverted) after this session's Chart-engine/Map-engine sweeps didn't fix this as a side effect**: the real WSL stack trace shows `ChartMapper.RenderLegends` → `RenderLegend` → `RenderLegendStyle` → `RenderLegendFont` → `MapperBase.GetDefaultFont()` → `FontCache.GetFont()` → `FontCache.CreateSafeFont()` → `new System.Drawing.Font(...)` throwing — this is in the RDL-to-chart-model *mapping* layer (`Microsoft.ReportViewer.Common`'s `OnDemandReportRendering` namespace), not the Chart engine's own rendering internals (`Microsoft.Reporting.Chart.WebForms`) that this session's sweeps targeted. Same permanent "Font construction is impossible on Linux" wall as `tasks/chart-default-font-cross-platform.md` already documents, just a newly-found, separate instance of it, one layer higher in the stack. Not fixed - needs the same larger, not-yet-scoped architectural change (routing `MapperBase.FontCache`'s callers through `IDrawingResourceFactory.CreateFont` instead of `new Font(...)`, which in turn needs the Chart engine's own model properties like `chartLegend.Font` to accept something other than a concrete `Font`) already flagged as out of scope there.
- **BMP/GIF/TIFF/EMF** stay Windows-only (SkiaSharp encode limitation for the first two, no portable equivalent at all for the last two).
- **No pixel-baseline tests yet** for the new Phase 2/3 fixtures (`ShapesOnlyReport.rdlc`, `RichTextProbeReport.rdlc`, and the pre-existing `SimpleTextboxReport.rdlc`'s new PNG coverage) - they assert well-formed output only, matching Gauge/Map's existing precedent (no baseline exists), not a pixel-exact regression guard. A future pass could add one, mirroring Chart's `ImageComparer.CompareToBaseline`.

## What this covers

`Microsoft.ReportingServices.Rendering.ImageRenderer/ImageWriter.cs` — the renderer behind the `IMAGE` format (TIFF/EMF export), used by `LocalReport.Render("IMAGE", ...)`. This is a **separate rendering extension from PDF**, despite living in the same `ImageRenderer` project folder and sharing the `Renderer`/`RichText` pagination pipeline PDF uses. `ImageWriter` draws through real `System.Drawing.Graphics`/`Pen`/`Brush`/`GraphicsPath` calls and `MetafileGraphics.cs`'s raw HDC/`Metafile` handling — this is exactly the GDI+/Metafile stack that PDF's own analysis (`docs/decisions.md`) confirmed PDF itself never touches. IMAGE does touch it, directly and unavoidably for EMF specifically (`Graphics.GetHdc()` has no cross-platform equivalent — same wall already called out as permanent for Chart's `SaveIntoMetafile` in `docs/platform-support.md`).

## Current gap

- `MetafileGraphics`/EMF (vector) is entirely GDI+-coupled with no portable equivalent — needs a real Windows HDC/`Metafile`, same permanent wall as Chart's `SaveIntoMetafile`. Guard rather than port; not further scoped here.
- TIFF/BMP/GIF/JPEG/PNG (raster) had two stacked blockers. **The first is fixed (2026-07-27):** `Graphics.NewPage` no longer builds its per-page surface via raw Win32 `GetDC`/`CreateCompatibleDC`/`CreateDIBSection`/`SelectObject` HBITMAP interop — it now uses a portable `new Bitmap(w, h, PixelFormat.Format32bppRgb)` + `Graphics.FromImage(...)`, the same construction `GraphicsBase.EnsureGraphics` already used for its own scratch HDC. **The second blocker remains open:** GDI+ itself cannot construct any `System.Drawing` object at all on Linux under .NET 10 (the Phase 0 spike finding in `docs/platform-support.md`) — so raster IMAGE output is still Windows-only today, just for a different, deeper reason than before. A real fix needs a Skia-backed raster surface, the same shape as Chart's `IRenderSurface`/`SkiaRenderSurface`/`GdiRenderSurface`, selected via a factory — this hasn't been scoped or attempted. Note `IRenderSurface` as it exists today isn't directly reusable as-is: it has no drawing API (`ImageWriter`'s `DrawLine`/`DrawRectangle`/`FillPolygon`/`DrawImage` calls have no Chart-side equivalent to borrow) and no TIFF case or multi-frame `SaveAdd` semantics in its `Encode` method — extending it, or building an `ImageWriter`-scoped sibling, are both open design questions.
- **Test coverage: added 2026-07-27** (`ImageWriterRdlTests.cs` — TIFF and BMP smoke tests, asserting well-formed magic bytes; `GaugeRdlTests.cs`/`SunburstChartRdlTests.cs` already covered PNG via IMAGE). All are Windows-only smoke tests; none are cross-platform-verified since the underlying GDI+ construction gap blocks that entirely today.

**Empirically confirmed under WSL, twice, one day apart (2026-07-27):**
- **Before the `Graphics.NewPage` fix** (via a throwaway scratch test against `LocalReport.Render("IMAGE", "<DeviceInfo><OutputFormat>TIFF</OutputFormat></DeviceInfo>")`, not committed): the failure happened at the very first page, before any drawing or text — `ImageWriter.BeginPage` → `Graphics.NewPage` called `Win32.GetDC(IntPtr hWnd)`, a raw Win32 P/Invoke (`user32.dll`), and threw `DllNotFoundException` immediately on Linux.
- **After the fix** (via the committed `ImageWriterRdlTests.SimpleTextbox_RendersToTiff`/`_RendersToBmp`, run under WSL): the crash moved, it didn't disappear. `Graphics.NewPage`'s `new Bitmap(...)` call itself now throws `TypeInitializationException`→`DllNotFoundException` for `gdiplus.dll`/`libgdiplus`, landing on the same "GDI+ can't construct anything on Linux" wall `docs/platform-support.md` already documents for Gauge/Map. This confirms the fix was real (it moved the failure point past the Win32-specific call) but confirms a genuine cross-platform TIFF path needs Skia, not just removing raw P/Invokes.

## Related upstream signal

Upstream `lkosson/reportviewercore` issue #42 ("PDF & Image generation fails on Windows Nano Server Docker container", open) reports the *same underlying dependency* — GDI+ and Uniscribe being unavailable — failing even on a **Windows** host (Nano Server is headless Windows with no GDI+/Uniscribe). This confirms the IMAGE/EMF renderer's GDI+ dependency is a real production concern beyond just "Linux support" — worth linking here since a future TIFF-via-Skia path would fix both the Linux gap and the headless-Windows-container gap in one move, unlike PDF's fix (which only had to address non-Windows, since PDF was already routed off Uniscribe's Windows-only shape/place split).
