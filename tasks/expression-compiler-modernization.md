# RDL expression compiler: sandboxing and single-file-deployment gaps

**Status: sandboxing — documented, permanent limitation (no code change). Single-file deployment — fixed and verified end-to-end (2026-07-27).** Both items were originally flagged generically (one line each, no detail) in `tasks/adapter-layer-refactor.md`'s "Related README compatibility gaps" list.

Both issues live in the same file: `Microsoft.ReportingServices.RdlExpressions/VBExpressionCodeProvider.cs`, which compiles RDL `=Expression` code via `Microsoft.CodeAnalysis.VisualBasic` (Roslyn).

## 1. No expression sandboxing exists (security) — permanent, documented limitation

Confirmed 2026-07-27: there is genuinely no sandboxing today. `ExprHostCompiler.Compile` still carries a `refusePermissions`/`AppDomain` parameter left over from the original CodeDom-era design, but it's a vestige with no effect under Roslyn — no permission-restriction or execution-isolation code is active anywhere in the compile/execute path.

**Conclusion (2026-07-27): not practically fixable in-process, and not going to be attempted.** AppDomain-based isolation — the only mechanism this codebase's vestigial `refusePermissions` parameter was ever built against — was removed entirely starting with .NET Core (there is no replacement primitive for loading and restricting untrusted code within the same process on modern .NET). The only realistic isolation options are external to this codebase: running untrusted reports in a separate process or container, sandboxed by the OS rather than the CLR. This isn't something `VBExpressionCodeProvider.cs`/`ExprHostCompiler.cs` can be patched to do — it would be a hosting-model decision made by whatever application embeds this library, not something the library itself can enforce. README's "What doesn't work" already states this limitation plainly ("Do not load and run reports from untrusted sources"); this entry exists so that stays a deliberate, permanent, documented decision rather than something a future session tries to quietly "fix" without understanding why it can't be.

## 2. Single-file deployment breaks expression compilation

Confirmed still real, not a stale note: `VBExpressionCodeProvider.cs` built Roslyn `MetadataReference`s via `Assembly.Load("...").Location` for the BCL assemblies every VB expression needs (`System.Private.CoreLib`, `Microsoft.VisualBasic.Core`, `System.Runtime`, `System.Text.RegularExpressions`, `netstandard`). `Assembly.Location` returns an empty string for assemblies bundled into a single-file publish; the existing `CheckAndAddReference` guard (`String.IsNullOrEmpty`/`File.Exists`) silently *skipped* that reference rather than throwing, so the actual failure surfaced later and more confusingly, as a genuine Roslyn compile error ("type not found") the first time any report contained a non-trivial expression — matching README's "What doesn't work" description.

### Fixed (2026-07-27): the BCL-assembly references

Added a second `CheckAndAddReference(List<MetadataReference>, Assembly)` overload that, when `assembly.Location` is empty or missing, falls back to `System.Reflection.Metadata.AssemblyExtensions.TryGetRawMetadata(assembly, out byte* blob, out int length)` — this reads the assembly's PE metadata directly out of the already-loaded module in memory, which works regardless of whether the assembly came from an on-disk file, a single-file bundle, or any other loader that leaves no `.Location`. Wrapped into a `ModuleMetadata`/`AssemblyMetadata` and turned into a `MetadataReference` via `.GetReference()` — the same standard pattern real-world Roslyn scripting hosts use for this exact problem. `Microsoft.ReportViewer.Common.csproj` already has `AllowUnsafeBlocks` enabled, so no project-file change was needed for the `byte*` pointer this requires.

All five `Assembly.Load(name)` calls (`CoreLib`/`VisualBasic.Core`/`Runtime`/`RegularExpressions`/`netstandard`) now route through the `Assembly`-typed overload. Verified: 0 build errors, `Chart.Rdl.Tests` 179/179 on Windows and 169/179 under WSL (the same 10 pre-existing/documented environment-only failures — 8 font-path ones plus the 2 known WORD-binary COM failures from `tasks/word-renderer-cross-platform.md` — zero new failures), confirming the fix doesn't regress the normal (non-single-file) path on either platform.

### Fixed (2026-07-27): the second, deeper single-file blocker in the *callers*

`options.ReferencedAssemblies` (a plain `CompilerParameters.ReferencedAssemblies` `StringCollection`, populated by `ExprHostCompiler.cs`/`ReportCompileTime.cs` before calling into `VBExpressionCodeProvider`) was fed **string file paths**, not `Assembly` objects — by the time a caller did `compilerParameters.ReferencedAssemblies.Add(typeof(ReportObjectModelProxy).Assembly.Location)`, an empty `.Location` under single-file publish had already collapsed to an empty string with no assembly identity left to recover. `VBExpressionCodeProvider`'s own `TryGetRawMetadata` fallback (above) couldn't help there — it needs the live `Assembly` object, which was gone by the time it reached `CheckAndAddReference(string)`.

Concretely: `ExprHostCompiler.cs` (~line 264-267) had a three-step fallback chain (`typeof(ReportObjectModelProxy).Assembly.Location` → `Assembly.GetExecutingAssembly().Location` → `Process.GetCurrentProcess().MainModule.FileName`) that still resolved to nothing useful under single-file publish (the first two are empty, the third points at the single native host executable, not a DLL containing `ReportObjectModelProxy`'s metadata). `ReportCompileTime.cs` (~line 232) had no fallback at all — a bare `.Location` reference that silently vanished the same way the BCL ones used to. Since `ReportObjectModelProxy` is the RDL expression host's core proxy type (`ReportItems!`/`Fields!`/etc. all resolve through it), losing this reference meant **any expression that touches report data at all** still failed to compile under single-file publish, even after the BCL-assembly fix above.

**Fix chosen: option (b) from the original proposed-tasks list below — a narrower special-case, not a `CompilerParameters` contract change.** Both `ReportObjectModelProxy` classes in this codebase (`RdlExpressions.ExpressionHostObjectModel.ReportObjectModelProxy` and `ReportProcessing.ExprHostObjectModel.ReportObjectModelProxy` — easy to conflate, a naming trap worth flagging explicitly) live in the same project/assembly (`Microsoft.ReportViewer.ProcessingObjectModel`), which `Microsoft.ReportViewer.Common` (home to `VBExpressionCodeProvider.cs`, `ExprHostCompiler.cs`, and `ReportCompileTime.cs`) already references directly — so there was no need to smuggle an `Assembly` reference through the string-typed `ReferencedAssemblies` collection at all. `VBExpressionCodeProvider.CompileAssemblyFromDom` now calls `CheckAndAddReference(roslynReferences, typeof(RdlExpressions.ExpressionHostObjectModel.ReportObjectModelProxy).Assembly)` directly, unconditionally, using the already-fixed Assembly-typed overload (with its `TryGetRawMetadata` single-file fallback). The two broken `ReferencedAssemblies.Add(...Location...)` calls in `ExprHostCompiler.cs`/`ReportCompileTime.cs` were removed outright rather than left as now-redundant dead code, since `GetCodeCompiler()` only ever returns `VBExpressionCodeProvider` (confirmed via `VBExpressionParser.GetCodeCompiler`) — there's no other consumer of that `StringCollection` entry to preserve it for.

**Verified end-to-end (2026-07-27):** a throwaway single-file-publish harness (`dotnet publish -p:PublishSingleFile=true --self-contained true -r win-x64`, not committed — scratch console app + a minimal RDLC with a `=Fields!Value.Value & "-" & (1 + 41).ToString()` expression) was published and run. It printed the expected `hello-42` result with exit code 0 — confirming the VB expression genuinely compiled and executed against real report data inside a real single-file, self-contained publish, not just that the BCL references resolve. The full `Chart.Rdl.Tests`/`DataVisualization.VisualRegressionTests` suites (183 + 137 tests, all of which compile and evaluate report expressions on the normal multi-file path) also pass unchanged, confirming no regression to the common case.

**Related upstream signal:** upstream `lkosson/reportviewercore` issue #183 ("replace GetExecutingAssembly with more proper assembly") reports exactly this shape of problem (a different call site — embedded-resource loading via `Assembly.GetExecutingAssembly()`) and proposes `typeof(SomeKnownType).Assembly` over `GetExecutingAssembly()` — the fix here goes one step further: it's not just *which* assembly gets identified, it's that `.Location` on *any* assembly (however identified) is empty under single-file publish, so the live `Assembly` reference has to be used directly rather than degraded to a path anywhere in the call chain. Confirms this is a recurring pattern across the codebase, not a one-off, exactly as originally suspected.

Separately, upstream PR #222 ("Upgrade to .NET 10 and optimize for single-file deployment") was closed unmerged/not-applicable (2025-11-22) with no recorded rationale — not useful as prior art.
